# Data ownership

This document is for anyone deciding which service is allowed to read or write
a given table before Phase 5 (per-module database isolation) locks that
decision in. It lists, for every one of the 26 Nest deployables in
[`services.yaml`](../../services.yaml) (see the generated
[`services.md`](./services.md) for ports and health routes), the database it
connects to, the TypeORM entities it registers, any table it reaches through
raw SQL instead of an entity, and what that combination actually means. It is
deliberately exhaustive rather than tidy — it is the seed of the Phase 5
inventory, not a polished summary — and it is built by transcribing each
deployable's `entities/` folder and by grepping for `query(`/`tablePath` in
its source, not by asking what the architecture is supposed to look like.

Two things this document is _not_: it does not repeat how migrations run or
how `synchronize` behaves (see the
[database migrations guide](../guides/database-migrations.md)); and a
"database / schema" cell is what [`services.yaml`](../../services.yaml)
declares, which — as several rows below show — is not always what the code
actually connects to.

## How to read the table

- **Entities** are the exported class names found under the deployable's
  `src/entities/` folder, transcribed as-is.
- **Raw SQL tables** come from `git grep -nE "query\(|tablePath"` against the
  deployable's own source tree — a table it reads or writes without going
  through an entity/repository for that table.
- A table name in **bold** is mapped, under the same or a different class
  name, by more than one service. Bold does not always mean "same physical
  table" — see the notes column and "What Phase 5 must decide" below, because
  schema and database qualification change the answer per case.

## What Phase 5 must decide

These are the tables (or table-shaped names) more than one service maps today,
and the specific question each one leaves open:

- **`users`** — `api-gateway` and `auth-service` both connect to
  `kartseek_db` with the default `public` schema and both declare
  `@Entity('users')`: this is one physical table read and written by two
  independent NestJS connections. `user-service` also declares a `users`
  entity, but connects with `schema: 'user'`, so it resolves to `user.users`
  — a third, separate table that Phase 5 needs to either retire, migrate into,
  or explain. Whichever table survives, only one service should own writes.
- **`taxi_vendors` / `taxi_drivers` / `taxi_rides` / ... (23 tables)** —
  modelled once by `api-gateway` in `kartseek_db.public` and once by
  `taxi-service` in `kartseek_taxi.taxi`. Different databases today, so no
  runtime collision, but two schemas for one domain, kept in sync by nothing.
  The gateway module's own comment marks this as transitional; Phase 5 is
  where "transitional" needs an end date.
- **`page_layouts`** — `api-gateway` (`public`) and `admin-service` (`admin`)
  each have their own copy. Different schemas, so different tables today, but
  worth deciding whether CMS layout data should live in one schema with one
  writer.
- **Commission, delivery, refund and report data** — `commission-service`,
  `delivery-service`, `refund-service` and `report-service` each have a
  Postgres schema declared in `services.yaml` that their code never connects
  to; all four persist exclusively in Redis today. Phase 5 cannot "split" a
  schema that was never populated — it has to first decide whether these four
  get a real table (and a migration path off Redis) or have their declared
  `database` entry in `services.yaml` corrected to `null`, the way
  `cart-service`, `loyalty-service`, `notification-service` and
  `search-service` are already declared.

None of this contradicts what [`services.yaml`](../../services.yaml)
declares — it is what the deployables' own source does with that declaration,
which for four of them is nothing.
