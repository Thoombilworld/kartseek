## 0. Method and honesty statement

- **What was inspected.** `apps/web/src/app/admin/**` (250 pages, 8 layouts), `packages/shared-core/src/{api,hooks,contexts}`, `apps/web/src/proxy.ts`, the 11 gateway admin controllers under `apps/api/apps/api-gateway/src/controllers`, the gateway guards/decorators/interceptors, `admin-service`, `audit-log-service`, every module backend's admin handlers and entities, migrations, seeds, specs and Postman.
- **How.** Static census scripts (route → RPC command → backend `@MessagePattern` handler; per-route market-scope detection; entity market-column scan; console endpoint → gateway route diff) plus targeted file reads. Counts below are reproducible from those scripts (`scratchpad/admin-census.js`, `mp-census.js` — copy the logic from §4 if the scratchpad is gone).
- **What was not done in this session.** No live probes against a running fleet. The live authorization proof that exists is the 2026-09-06 script run (`apps/api/scripts/verification/regional-isolation-authz.mjs` 36/36, `regional-isolation-e2e.mjs` 67/67) which covers promotion routes only. Every finding marked _static_ below must be confirmed live during Plan A/B execution; the plans include those probes as steps.
- **Read every 200 with suspicion.** Per the repo's own history (`project_fabricated_fallbacks`, `project_admin_stub_endpoints`), a 200 from an admin route proves nothing. This audit classifies a route as _real_ only when the handler reaches a service, a repository or Redis.

## 1. Review of the existing implementation plan

The most recent plan touching admin is `docs/superpowers/plans/2026-09-06-marketplace-customer-frontend-plan.md`, section "Done in the fourth pass (regional promotion isolation)", with its audit in `docs/audits/2026-09-06-marketplace-customer-frontend-audit.md` §16.

**What it delivered (verified in code):**

- Regional identity is a signed claim: `users.region_code` + `users.region_locked` (migration `1786501600000-UserRegionScope`), signed by `AuthController.issueTokens` in `apps/api/apps/api-gateway/src/controllers/gateway.controller.ts`, read by `apps/api/libs/security/src/jwt.strategy.ts`. `SUPER_ADMIN` is global; a locked `ADMIN` is the regional admin. Seeded `qa-admin@kartseek.com` (QA) and `india-admin@kartseek.com` (IN).
- `apps/api/apps/api-gateway/src/guards/market-scope.ts` (`marketScopeOf`, `resolveMarket`, `assertRecordInScope`) applied to 28 of the 198 marketplace admin routes (flash deals, nominations, promotions, coupons, banners, bank/exchange offers).
- Backend `assertInMarket` (private method on `MarketplaceAdminService`) on those handlers; per-market cache keys and purges; orders persist `region_code`/`currency`; cart lines per market.
- The console lock is read from the token (`regionLocked` badge, no market dropdown).

**What it explicitly left open:** dashboard fixture widgets, sponsored products, B-10 (cancel releases stock), GB/US as trading markets.

**What it never covered, and this audit now finds broken:**

1. Every admin route that is not a marketplace promotion: 158 routes in the other ten admin controllers and 170 non-promotion marketplace routes carry no market scope (§4.2). A regional admin is confined for coupons and banners, and free everywhere else.
2. The console's _role_ is still fabricated client-side (`role: 'SUPER_ADMIN'` for every admin in `admin/login/page.tsx` line 257), so the shell's `hasRole('SUPER_ADMIN')` gate and the edge's cookie check pass only because the console lies (§5, SEC-03).
3. RBAC beyond two roles: `RolesGuard` supports `perm:` keys but no route uses them, the token carries no permissions, and nothing persists roles or staff (§5, SEC-06).
4. The audit trail: three disconnected stores, the one the console shows being in-memory fake data (§5, SEC-08).
5. Validation: zero DTO-validated bodies across all 356 admin routes (§5, SEC-09).
6. The other modules' admin backends: 76 gateway commands have no handler (§4.1).
7. Its proof is script-based, not in the test suite; no unit test covers `market-scope.ts`.

**Verdict.** Keep the identity model (claim-based scope, `SUPER_ADMIN` global, locked `ADMIN` regional) and the `resolveMarket`/`assertInMarket` pattern; they are correct and proven. Extend them to every admin route, move `assertInMarket` into a shared library, delete the dead `RegionGuard`/`RegionIsolationGuard`, and turn the scripts into regression specs. Do not rewrite the marketplace promotion isolation.

## 3. Architecture as found

```
Browser  ──►  apps/web/src/proxy.ts (edge: /admin needs cookie kartseek_user_role === 'SUPER_ADMIN')
         ──►  apps/web/src/app/admin/layout.tsx (client gate: hasRole('SUPER_ADMIN'); nav filtered by hasPermission())
         ──►  packages/shared-core/src/api/admin-*.ts + modules/admin-marketplace-api.ts (Bearer from getAuthToken(); ?country= from selectedRegion)
         ──►  api-gateway /api/v1/admin/**  (JwtAuthGuard + RolesGuard(ADMIN|SUPER_ADMIN) per controller; market-scope.ts on 28 routes)
                 ├─ admin-core      ──TCP──► admin-service (users, KYC, Redis audit blob, revenue, page layouts)
                 ├─ admin-marketplace ─TCP─► marketplace backend (+ commission, payout, wallet, loyalty, order, refund clients; Redis)
                 ├─ admin-grocery / -taxi / -hotel / -restaurant / -pharmacy / -doctor ─TCP─► module backends
                 ├─ admin-seo / admin-layout (gateway-held repos) · ddos-admin (DdosMonitorService)
                 └─ AuditInterceptor ──Kafka audit.log──► audit-log-service (Mongo) [not readable back through the gateway]
Identity: users.role + users.region_code/region_locked ──► JWT {sub, role, regionCode?, regionLocked?, sellerType?, type, jti} ──► JwtStrategy ──► req.user
```

Two `users` entity mappings exist for the same table: the gateway/auth-service mapping (has `regionCode`, `regionLocked`, `status`, no `country`) and user-service's (has `country`, `status`, KYC flags). `admin-service` queries `users.country` through the query builder, so customers _do_ have a market column; staff scope and customer market are different columns on the same row.

### 4.2 Market scope coverage

`resolveMarket`/`marketScopeOf`/`assertRecordInScope` appear in 28 marketplace routes and nowhere else. Routes a **regional admin can call across markets today** (static; the promotion routes are proven confined, everything else is proven _unconfined_ by absence of any predicate):

- Core: `GET /admin/users?country=IN` (returns any market's users), `PUT /admin/users/:id/ban|unban`, `GET /admin/kyc/pending`, `POST /admin/kyc/:id/approve|reject`, `GET /admin/reports/revenue`.
- Marketplace: sellers list/pending/detail/approve/reject/suspend/reactivate/block; products list/pending/detail/approve/reject/request-correction/publish/unpublish/suspend/feature; listings approve/reject; seller-approvals, product-approvals, customers + block, complaints, disputes, reviews flag/hide, returns, refunds, payouts approve/process/retry, commissions rate-card/overrides, seller-wallets adjust, wallet freeze/unfreeze, loyalty adjust, all analytics.

- Grocery: stores approve/suspend, orders, products, flash deals approve/reject, settings.
- Hotel/restaurant/pharmacy/doctor: every route that has a handler.

The legacy `guards/region.guard.ts` (`@RequireRegion`) and `libs/security/src/region-isolation.guard.ts` are applied to no route; the former compares case-sensitively and allows any request that names no region. Both are dead code to delete.

### 4.5 Console → API contract

- 99 of 250 pages call a list route and then filter by market in the browser (`useMarketplaceRegionFilter`, `useTaxiRegionFilter`, `useGroceryRegionFilter`), matching on human-readable country _names_ against ISO codes — a fetch-everything-then-hide pattern. For a global admin it downloads every market; for a regional admin on an unscoped route it is the leak.
- 16 pages ship fixture data (`MOCK_*`, `sampleOrders`, `mockData`, `DEMO_STAFF`, `INITIAL_ROLES`), and 12 top-level pages import no API at all: roles, staff, security, two-factor, settings, audit-logs, notifications, system-health, sos, support, analytics, refunds.
- The dashboard mixes a real `getDashboard()` with fixture `recentActivity`, `hourlyData` and `modules` arrays; the header's notifications dropdown is a literal list ("v3.12.0 deployed to all regions").

## 7. UX findings (feeds deliverable 3)

- 144 pages hand-roll `<table>`; 25 have pagination; 3 have bulk actions; 2 have breadcrumbs; 6 use native `confirm()`; 47 have an empty state; 69 a loading state. There is no shared admin table, dialog, skeleton or toast in `packages/shared-ui` (it has form `Field`, `CountryFlag`, `CurrencyDisplay`, `DismissOnEscape`); `components/admin/marketplace/*` holds a small toolkit used only by marketplace pages.
- 111 admin files hard-code `₹` (violates the localization rule in `project_localization_architecture`); regional admins in QA/AE/SA see rupee symbols on several pages.
- Navigation: 44 top-level items in 6 sections plus 7 module sub-navs (marketplace 59 items); the module sub-layouts are seven different components; one dead link; Loyalty appears twice; three items without a permission key.
- No global search, no breadcrumbs, no keyboard-first table interactions, no consistent confirmation dialog, no activity timeline outside marketplace.
- Responsive: the shell has a mobile drawer; tables overflow without a scroll container on most module pages (to be measured with the responsive harness in Plan E).

Design rule adopted in the spec: **global by declaration or scoped by column**. Every entity is either declared global (brand, category, attribute, specialty, cuisine, amenity, static page) or must carry `region_code` directly or resolve it through one join to an owner that does (order → seller/store, review → product → seller, appointment → clinic, hotel-room → hotel).
